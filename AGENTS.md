# AGENTS.md — Echo11 development guide

This is the source of truth for coding agents working in this repository. Read it before making changes, then read the task-specific project skill listed below.

## Start here

1. Inspect the relevant route, component, action, and type before editing.
2. Preserve uncommitted work. It belongs to the user unless the task clearly says otherwise.
3. Reuse existing patterns and UI primitives instead of introducing parallel systems.
4. Validate the change at the end. Run `npm run build` after meaningful application changes.

## Commands

Run from the repository root.

```bash
npm run dev          # Start the local development server
npm run lint         # Lint application source files
npx tsc --noEmit     # Type-check without emitting files
npm run build        # Create the production build
```

Development output is isolated per port (`.next-dev-3000`, `.next-dev-3001`, etc.); production builds use `.next`. This prevents simultaneous previews and builds from overwriting server chunks. Use `npm run dev -- --port 3001` when a second preview is needed.

There is no automated test suite or test script. Do not invent or run Jest/Vitest commands. Use the lint, type-check, build, and task-appropriate manual verification instead.

### Authentication boundaries

- `/lab/(auth)` contains unauthenticated lab routes and redirects signed-in users appropriately.
- `/lab/(authenticated)` performs the server-side lab access check and loads user preferences.
- `/client/(protected)` is the role-aware client workspace. Admins and members are redirected to `/lab/dashboard`.
- `/portal` has its own legacy auth flow. Keep its revalidation paths working while it remains in the repository.
- Use `createClient` from `@/lib/supabase/server` in server code and `@/lib/supabase/client` in client components.

## Code conventions

- Use the `@/` alias for internal imports.
- Import in this order: React, framework/external packages, then internal modules.
- Use PascalCase for React components and exported object types; camelCase for variables and functions.
- Prefer interfaces for reusable object shapes and `type` for unions.
- Do not introduce `any`; use defined types or `unknown` with a type guard.
- Use `next/link` for internal navigation.
- Use `date-fns` for date formatting.
- Avoid `console.log` in committed application code. Error logging with meaningful context is appropriate in actions.

### Types

`Project` and `Service` have distinct marketing and lab shapes. Import marketing types from `@/types` and lab types from `@/types/lab`; do not interchange them.

### Server actions

- Start action modules with `'use server'`.
- Get the authenticated user before performing user-scoped mutations.
- Return structured success/error results where practical.
- Handle async failures with `try/catch`, log contextual server errors, and keep user-facing errors clear and non-sensitive.
- Revalidate every affected surface. For client-visible data, update both `/client` and the retained legacy `/portal` paths through `client-surface-revalidate.ts` when the existing action pattern does so.
- Record activity entries where the surrounding feature does.

## Design system

- Dark-first: black and near-black surfaces, white/off-white content, and cyan `#00E5FF` as the deliberate accent.
- Fonts: Syne (`font-sans`) and JetBrains Mono via the `--font-geist-mono` variable (`font-mono`).
- Use the Tailwind design tokens: `background`, `foreground`, `card`, `muted`, `border`, and `accent`.
- Prefer sharp geometry (`rounded-none` or restrained rounding), fine borders, and selective glass effects such as `glass`, `lab-glass`, and `lab-card`.
- Reuse `Button`, `LabButton`, `Card`, `LabCard`, `Container`, and page/layout wrappers before creating equivalents.
- Keep motion restrained, purposeful, and compatible with reduced-motion preferences.

## Data and Supabase

- `supabase/migrations/` is the canonical, ordered database-change history. Treat `docs/supabase-schema.sql` as a reference/bootstrap document, not the authoritative current schema.
- Put new database changes in a timestamped SQL migration. Include schema, indexes, RLS policies, and backfill-safe behavior required by the change.
- Design access by role and ownership. Do not loosen RLS merely to unblock a UI.
- Do not run `supabase db push`, link a project, or apply remote migrations unless the user explicitly asks for that external change.
- `.env.local` is ignored. Start from `.env.example`; never commit secrets.
